# ADR001 — обновление открытых вкладок при смене аккаунта

Статус: решение принято основным агентом для Q03; результаты реализации проверяются отдельно в docs/evidence/Q03/review.md. Источник — реально воспроизведённый Chromium-сценарий: форма студентаA остаётся в первой вкладке после logout/login студентаB во второй. Прежний history.js отслеживал только pageshow.persisted.

## Решение

Использовать существующую CSRF-cookie как локальный маркер перехода вход/выход, сохраняя авторизацию штатными Django sessions и CSRF middleware. Login уже меняет CSRF secret; logout дополнительно вызывает штатный rotate_token после удаления сессии. Ни raw session key, ни новый authentication token браузерному JS не передаются.

Общий history.js подключается единожды в accounts/base.html для входа и приватных/error страниц. При загрузке запоминается текущее значение CSRF-cookie только в памяти JS. При focus/visibilitychange оно сверяется с актуальным: неизменённая cookie сохраняет незавершённую форму; изменение очищает старый DOM, показывает нейтральное сообщение со ссылкой повторить и инициирует GET на главную. pageshow.persisted вызывает сетевое повторное открытие с предварительным удалением старого содержимого: прежний GET URL либо главную, если документ получен POST. Тип запроса берётся из безопасного data-request-method общего body. Используется location.replace, а не reload: это предотвращает повтор POST и диалог resubmission на странице ошибки/конфликта формы. Retry-ссылка ведёт на тот же безопасный GET.

BroadcastChannel передаёт только сигнал «перечитай состояние» при загрузке страницы. В сообщении нет cookie/token/ID/ФИО/текста формы; получатель сверяет свою cookie и не считает сигнал доказательством авторизации. При отсутствии API или ошибке его создания работает проверка при возвращении фокуса/видимости. Постоянного polling и хранилища персональных данных нет. Повторные события не должны создавать цикл навигации.

## Границы и последствия

- `SESSION_COOKIE_HTTPONLY=True` сохраняется. Для этого UI механизма используется текущая стандартная доступная JS CSRF-cookie `csrftoken`; её значение не логируется и не попадает в BroadcastChannel/storage/evidence. При будущем изменении CSRF_COOKIE_NAME или включении CSRF_COOKIE_HTTPONLY механизм требуется пересмотреть.
- Серверные права не зависят от JS. Старый CSRF hidden token после нового входа отклоняется middleware; тест должен подтвердить это с JS отключённым. GET данных и POST действий всегда проверяют актуального пользователя/владельца.
- Истечение сессии, отзыв роли/scope или деактивация без login/logout могут не менять CSRF-cookie. Их обнаруживает сервер при следующем запросе; мгновенная фоновая/offline проверка не обещается.
- Открытая вкладка без JS сохраняет исторически отрисованный DOM до навигации; это не даёт права на следующий серверный запрос или действие. UI очистка не заменяет проверку доступа.
- Произвольный focus при прежней cookie не отправляет запрос и не теряет текст. При обнаруженной смене старый приватный DOM удаляется до reload; при недоступности сети пользователь получает обычное повторное открытие/ссылку, а не ложный success.
- Новый endpoint/HMAC/contextprocessor и отдельный API не требуются. CSP/proxy/HTTPS проверяются в D02; этот ADR не подтверждает production-контур.

Критерии: реальные две вкладки одного context, отдельные независимые contexts, stale POST, выход/Back/Forward, сохранение формы при обычном focus, работа без BroadcastChannel, отсутствие циклов и секретов в сообщениях. Фактическое использование BFCache фиксируется отдельно от синтетического теста обработчика.
