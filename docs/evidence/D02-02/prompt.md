# D02-02 — состав образов, известные уязвимости и безопасная диагностика

- Исполнитель `gpt-6.1-sol / low`, `fork_turns=none`, один writer без субагентов. Исходный HEAD `архивная-версия`, дерево чистое.
- Читать TASK/AGENTS, STATE/PLAN D02-02, ARCHITECTURE §§10/13/14, ADR002, docs/licenses.md, docs/operations/production.md, D02-01 prompt/implementation/review и фактические Dockerfiles/runner/tests.
- Требования SEC-02, LIC-01, TECH-03/04/06. Публичного деплоя, сервисных учётных данных, хостинга, покупки/туннеля нет. Только собственные локальные QA ресурсы.

## Законченный результат

1. Воспроизводимый аудит точных production images app/PG/Caddy: SBOM/OS package inventory, Python closure, Go build modules/runtime и bundled native libs, хеши/идентификаторы образов, дата/версия scanner и базы, raw безопасные machine-readable результаты + компактное summary. Не сканировать произвольный пользовательский image/DSN/директорию. Собирать production Caddyfile, не подменённый QA TLS config, для artifact inventory. Build context allowlist из D02-01, без .env/keys/private/source git history. Не создавать generic audit framework: narrow helper `scripts/verify_image_audit.py` с собственным lifecycle, допускается небольшой общий build-context helper при необходимости. Не копировать целиком 661-строчный TLS runner.
2. Scanner: официальный Trivy v0.76.2 (latest release проверен root по https://github.com/aquasecurity/trivy/releases/tag/v0.76.2 на8ноября); version+SHA256/digest и первичный источник подтвердить перед выполнением. Избегать floating latest и старых compromised releases. Можно standalone binary в /tmp с проверкой официального checksum или pinned tool image. НЕ монтировать Docker socket, host home или корень проекта в scanner; не privileged. Предпочтительно собственные images export через `docker save` в закрытый /tmp и локальный scanner `--input` (без публикации образа/кода в облако). DB скачать отдельно из официального OCI source, записать timestamp/schema/hash; scan offline/skip-db-update после успешного download. Только vulnerability/license, без скрытого отбрасывания unfixed/low findings. Не выдавать tool/network failure за no findings, не игнорировать CVE ради зелёного exit. Точные flags/версии проверить по первичным docs.
3. Реально проверить app, PG и Caddy. Разделять OS, Go/stdlib, Python и распознаваемые bundled libs; scanner не обещает обнаружение каждой native библиотеки. Отдельно перечислить `psycopg_binary.libs`, runtime libpq и OpenSSL из самого image (Python ssl и bundled SSL не путать), Argon2 wrapper/lib и license files. OS copyrights/common licenses и Python notices должны сохраняться. Source URLs/versions и SHA256 notices в manifest; не записывать raw image archives, dumps, private keys, state/env в evidence. SBOM только packages/versions/license/paths внутри image и технические hashes; без user data.
4. На findings сначала сообщить root компактно: affected image/package/version, CVE/severity/fix availability, первичный advisory URL. Root определяет изменения Dockerfile pins/packaging/lock. Без такого решения НЕ менять pyproject/lock, версии/базовый дистрибутив/схему или приложение. Не объявлять scanner labels юридическим заключением; спорные/unknown лицензии и вложенные notices передать root для проверки. Root ведёт финальный docs/licenses.md; ты подготовь безопасные inventory/источники и при необходимости предложение о недостающих notices. Исходники third-party кода не выполнять и не тащить весь vendor tree в Git. Если нужен новый текст лицензии в image — exact upstream text+hash+источник, сначала root approval конкретных файлов.
5. Восстановить операционные логи Caddy вместо `output discard`: safe JSON INFO/WARN/ERROR на stdout/stderr, не включать access log. Удалять целиком request/response headers, URI/query, cookies/body/IP/user data/trace fields и любые небезопасные error поля; оставлять действительно полезные level/logger/msg/событие/технический status. Сам msg/error может отражать клиентский ввод — не считать удаления request поля достаточным. Если нужен более строгий allowlist/event replacement, используй штатные Caddy encoders/filters, без собственного plugin и debug endpoint. Сохранить TLS/infra диагностику (старт, TLS maintenance/error, upstream failure), формат проверить настоящим Caddy validate/adapt/runtime, не только строковыми asserts. Приватность важнее точного текста ошибки.
6. Дополнить `scripts/verify_production.py` узкими assertions: logs не пусты и содержат ожидаемую operational event/upstream failure, но unique sentinels из пути/query/заголовков/Cookie/Authorization/body/искусственно большого запроса не появляются. Триггерить реальные413/403/404/502/DB503; safe source request logs приложения сохранены. Проверить JSON shape, отсутствие request/resp_headers/IP/user/URI fields на HTTP-error events и обычном startup. Не публиковать raw runtime logs с секретами в evidence — только sanitised технические aggregates/schema. Никакого blanket discard как способа пройти тест. Текущие CSP/HTTPS/cookies/CSRF/roles/body cap/proxy trust не ослаблять.
7. Запустить настоящий TLS default rehearsal после изменения Caddy, с ownership cleanup и явным empty env-file (NUL native Windows /dev/null Linux). Передать freeze, что изменилось, точную команду root independent rerun. Добавлять новые unit tests только по реальному риску (audit failure/status/ownership/redaction), не зеркала Caddyfile. Полный regression358 остаётся baseline; полный прогон нужен при изменении app/settings/deps, при одном logging/helper изменении достаточно целевых тестов и реального TLS smoke с root acceptance. Не запускать два pytest на одной БД. Не переписывать исторические PNG.

## Среда и безопасность

- uv0.12.1, Python3.13.14; `.venv/bin/python`, uv `/home/local-user/.local/bin/uv`. /tmp/deanery-python,/tmp/deanery-uv-cache,/tmp/deanery-browsers. При исчезновении среды восстановить locked interpreter, не менять system Python или lock.
- Native Docker `/mnt/c/Users/local-user/AppData/Local/Programs/DockerDesktop/resources/bin/docker.exe`, штатная escalation. Endpoint только фактически local unix/npipe (reuse require_local_endpoint). Сейчас engine29.6.2 доступен. Read-only registry downloads разрешены, без Docker login/PAT/облачной загрузки images.
- QA own unique project/resources/labels. Перед build mutation подтвердить отсутствие тега; пометить track до mutation/timeouts. Cleanup exact owner-label перед удалением и проверка отсутствия, при failure продолжать безопасный cleanup/выдавать nonzero. Ошибки daemon не принимать за missing. SIGTERM cleanup, Python-O отказ, no raw exceptions/Playwright calllogs. Не prune, не изменять/останавливать user dev5432/8000, не монтировать пользовательские пути, не читать .env/SSH/configcredentials. Docker CLI default autoload .env исключить явным пустым env-file.
- Image save может быть большим: stream subprocess stdout в собственный /tmp file, не печатать/держать гигабайты base64 в контексте. Trivy cache только свой /tmp, не домашний каталог. В `docs/evidence/D02-02/` только безопасные reports/SBOM/metadata, не binary archives/scanner cache/private state.
- В отчёте точно различать scanner completed/no findings, findings requiring remediation, unsupported/manual native coverage и blocked network. Нельзя молча закрыть LIC-01/весь D02 или гарантировать безопасность сайта.

## Владение

Разрешены `deploy/Caddyfile`, `scripts/verify_production.py` только build helper extraction при необходимости+logging assertions, новый `scripts/verify_image_audit.py` и узкий companion helper в scripts, `tests/test_image_audit.py`, `tests/test_production.py` только целевые новые проверки, `docs/operations/image-audit.md`, `docs/operations/production.md` только актуальная logging/audit инструкция, `docs/evidence/D02-02/implementation.md` и безопасные audit/SBOM/results JSON. Любые Dockerfile/pin/dependency/license text изменения сначала конкретно согласовать с root. Root владеет prompt/review/STATE/PLAN/ARCH/licenses/versioning и прежними SHA confirmation.

Исполнитель не принимает свой результат. До root accepted и отдельного staged allowlist нет commit/push; затем main/origin, обязательный атрибуция команды, без force/amend/обхода hook. Пользователь уже разрешил обычное версионирование, повторного вопроса ему не требуется.
