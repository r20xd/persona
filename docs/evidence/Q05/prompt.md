## Законченный результат

Добавить воспроизводимую проверку, реально доказывающую сохранность после restart web/db и dump→отдельная БД→повторное чтение. Не выдавать её за production backup, offsite encryption или готовый D04. Проверка запускается явно отдельно от обычного pytest, не требует Docker-in-Docker в CI.

1. Самостоятельно создаёт только собственные уникально именованные изолированные ресурсы PostgreSQL17.11 с pinned image из deploy/compose.local.yaml, loopback, без host mounts. Для этой проверки нужен собственный named volume и настоящий restart PG-процесса. Использовать случайное уникальное имя и не принимать существующий контейнер/volume/DSN пользователя. QA trust допустим только в disposable loopback среде; не переносить в dev/prod.
2. На пустой БД выполняет migrate и seed_demo, создаёт дополнительную настоящую заявку через форму студента, обрабатывает через scoped оператора, сохраняет событие/прочтение; сохраняет идентификаторы, статус/версию, историю, hash пароля (в памяти, не в логе), опубликованный результат/занятие и отметки прочтения. Первый этап должен использовать DEBUG=False Gunicorn/WhiteNoise и реальный вход браузером, а не только ORM.
3. Останавливает/запускает только собственный web-процесс с тем же SECRET_KEY и DB, затем restart только собственного PG контейнера. После готовности повторно читает сохранённые данные и проверяет аутентификацию/session persistence, прямой доступ ко своей заявке и отказ второму студенту. При недоступной БД readiness503, после восстановления200; не выводить DSN/traceback или персональные данные в отчёте.
4. Делает pg_dump в закрытый временный файл/stream, восстанавливает pg_restore с обработкой ошибок в другую БД внутри собственного тестового PG. Исходная БД не удаляется/не перезаписывается. Переключает только собственный web на восстановленную БД, повторяет вход/чтение/изолированность и сравнивает сохранённые значения. Дамп/пароли/session cookies не коммитить и не печатать; временные файлы удалить. Фактические команды, этапы и итог — безопасный компактный JSON или текст без секретов.
5. Дополнить PostgreSQL regression тестом upgrade схемы предыдущего этапа с существующей заявкой/историей → все текущие leaf migrations. Использовать historical models / MigrationExecutor в отдельном тесте, восстановление leaf schema в finally. Не повторять старый тест удаления requests таблицы, не удалять данные реальной dev-БД. Проверить соответствие текущим leaf migrations, парольный hash, профиль, оценки/занятие, request UUID/status/events. Нет новых миграций ради теста.
6. Повтор seed после restart/restore не меняет сохранённые данные. Проверка должна завершаться ненулевым кодом при расхождении/сбое и наконец убирать только собственные ресурсы, в том числе при исключении. Никаких broad prune/down -v, убийства чужих портов/процессов и удаления по одному prefix без точного ownership. Не оставлять сервер. Не считать docker restart, миграцию или restore успешными лишь по старту команды: дождаться готовности и проверить данные.

Закрытые случайные demo-пароли только env/getpass, не argv/лог. Не объявлять проверки остальных Q/D выполненными.
