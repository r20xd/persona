## Цель и контракты

1. Реализовать `seed_demo` как безопасный общий bootstrap двух студентов и scoped оператора, учебных данных, оценок, объявлений, сроков и разных заявок. Использовать существующие provision-команды/сервисы. Пароли только private env/getpass, никогда argv/логи; не менять существующие хеши, роли, scope, результаты, прочтение, события, статусы и действия пользователя. Для заявок стабильные submission UUID; переходы выполняются только для впервые созданной фикстуры. Повтор и конкурентный запуск не сбрасывают пользовательские состояния. Семантически несовместимый seed должен дать явную ошибку, а не переименовать/перепривязать чужие данные.
2. Реализовать `extend_demo_schedule`: только добавляет будущие отсутствующие занятия по стабильным ключам. Не двигает уже созданные/изменённые занятия и историю, не сбрасывает grades/заявки. Начальный `--anchor-date` по умолчанию текущая московская дата, исходный период и предыдущая неделя + минимум шесть недель вперёд согласно архитектуре. Сохранить устойчивость исходной даты при повторе seed без параметра. Для добавления стабильного metadata/DB constraint допустима миграция, если необходима; объяснить выбор. Не изменять календарь ОС и не подменять реальные текущие даты демодатой.
3. `apps/dashboard/`: настоящая студенческая `/`, профиль по `/profile/`, корень оператора по-прежнему ведёт в очередь. Сводка из серверных scoped selectors: ближайшее актуальное занятие/экзамен с преподавателем/аудиторией, заметные текущие изменения, ближайшие собственные дедлайны непосредственно из БД, активные заявки, опубликованный учебный итог, свежие уведомления/объявления и unread. Для учёбы использовать текущий семестр, при его отсутствии понятный fallback и название периода; не раскрывать будущие/черновые результаты. Отменённое занятие не показывать ближайшим. Deadline с опубликованным своим результатом не выдавать за несделанную работу; просрочка не доказывает отсутствие сдачи.
4. Главная — композиция, не новое хранилище. Те же правила владения Enrollment/StudentProfile, announcement audience и user role/active. No-store, login, CSRF/logout/BFCache остаются. Ссылки ведут к реальным разделам, пустое состояние честное, данные не заменяются preview. Длинный контент/360px/desktop, клавиатура и заметка конкурсного концепта. Сохранить одобренный стиль. Навигация пять пунктов + профиль и сессия внутри Учёбы должна связывать реальные страницы; не ломать существующие URL names.

## Проверки и приёмка

- PostgreSQL: первый seed, повтор после изменения заявки/оценки/прочтения/пароля/занятия, сохранение идентификаторов/истории и статусов, продление только добавляет будущее; два студента с разными данными.
- Главная: guest redirect, operator redirect, inactive/неполный профиль, same-group и other-group чужие данные/счётчики отсутствуют, draft/future grades отсутствуют, отмена и московская дата, честное empty и bounded queries без N+1.
- Chromium: полный путь login → dashboard → schedule/grades → создать заявку → отдельный operator process → студент видит статус/уведомление → повторный вход сохраняет данные; второй студент не видит заявку. 360/1440, CSS200 и computed style, без overflow. Новые screenshots только с UPDATE_EVIDENCE=1 для конкретного нового test-модуля; исторические PNG не переписывать.
- Ruff check/format, Django check, makemigrations --check --dry-run, полный suite по очереди (не два процесса на одной test_deanery).
- Отчёт: конкретные команды/результаты, список файлов, ограничения, ресурс QA для независимой проверки родителем. Публичный сайт/CI/физический телефон не объявлять проверенными.
