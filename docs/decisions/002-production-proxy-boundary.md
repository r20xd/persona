# ADR002 — граница доверия Caddy и приложения

Статус: архитектурное решение для D02-01. Оно не означает, что контур уже собран или опубликован; результаты исполнения и независимой проверки фиксируются в `docs/evidence/D02-01/`.

## Контекст

Приложение использует Django sessions/CSRF и ограничение входа Axes по username+IP. В локальной среде IP берётся из фактического `REMOTE_ADDR`. После появления reverse proxy этот адрес указывает на Caddy. Без отдельного решения приложение либо объединит посетителей за одним адресом прокси, либо начнёт доверять заголовку, который может прислать сам посетитель.

## Решение

Используем один непосредственный публичный reverse proxy, Caddy, без CDN и второго балансировщика. Веб-приложение и БД не имеют опубликованных портов. Caddy/app соединены отдельной внутренней сетью; app/db — другой внутренней сетью. Только Caddy дополнительно подключён к edge-сети для будущего ACME. Это не доверие ко всем Docker/private networks.

Caddy перезаписывает `X-Forwarded-Proto` реальной схемой соединения, `X-Real-IP` — адресом непосредственного посетителя; входные XFF/Forwarded не используются для установления доверенного IP. Django сохраняет `SECURE_PROXY_SSL_HEADER` при этой сетевой границе. Публичный HTTP всегда перенаправляется на HTTPS, независимо от присланного клиентом XFP.

Production использует отдельный Axes IP callable. Он принимает один синтаксически корректный `X-Real-IP` только от peer, попавшего в явно настроенный `DJANGO_TRUSTED_PROXY_CIDRS`. CIDR соответствует маленькой frontend-сети Compose, а не всей подсети хоста. Обязательная production-конфигурация отклоняет отсутствующие/ошибочные значения и `/0`. Непроверенный или некорректный header не заменяет фактический peer. `REMOTE_ADDR` глобально не переписывается; локальный/test callable остаётся прежним. Изменение выполняется на сервере без новых публичных endpoints.

Health checks внутри контейнера обращаются по HTTP loopback только к точным `/health/live/` и `/health/ready/`, с разрешённым Host. Только эти технические пути исключаются из Django HTTPS redirect. Они возвращают минимальный JSON и не раскрывают конфигурацию. Остальные пути сохраняют HTTPS redirect и Secure cookies. HSTS остаётся0 до проверки настоящего публичного HTTPS, без preload/includeSubDomains.

Конфигурация Caddy и PostgreSQL init поставляется в маленьких производных образах без секретов; host project/.env/SSH не монтируются. Пароли передаются при запуске из частной конфигурации, не через build args или слои. Доступ приложения к БД выдаётся отдельной ролью без superuser/createdb/createrole; миграции запускаются отдельной однократной командой.

## Проверяемые последствия

- Unit tests различают trusted/untrusted peer, IPv4/IPv6, один IP и некорректный/составной header, неправильную production-конфигурацию. Существующий локальный тест запрета доверия к XFF сохраняется.
- TLS rehearsal использует реальный Caddy, локальный CA в собственном томе и loopback-порты. Python HTTPS-проверка доверяет только извлечённому QA CA и проверяет hostname; browser exception для этой QA CA не выдаётся за проверку публичного сертификата. CA не устанавливается в ОС.
- Поддельные XFF/X-Real-IP не меняют ключ IP в Axes; поддельный XFP не отменяет HTTP redirect. App/DB не достижимы через опубликованные порты. CSP и cookies проверяются на настоящем ответе Caddy и браузерным путём.
- Если появится CDN, второй proxy, другой frontend subnet или прямой доступ к Gunicorn, это решение необходимо пересмотреть до публикации такого контура. Docker/host administrator находится вне этой модели изоляции.

Полный аудит native/OS состава и notices собранных образов, публичные сертификаты/сеть РФ, rollback и backup остаются следующими подэтапами. Локальная подготовка D02 не отменяет V2 перед первым публичным релизом и согласование расходов на хостинг.
