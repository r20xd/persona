# Работа архитектора и исполнителя

Рабочий процесс проекта связан с TECH-05 и SUB-04. Требования конкурса, архитектура, правила команды и статус собраны в [README](../../README.md).

## Роли и границы

Родительский агент **gpt-6.1-sol / high** проектирует архитектуру, формулирует ограниченные задачи, принимает решения по контрактам и независимо проверяет результат. Исполнитель **gpt-6.1-sol / low** пишет код и исправляет замечания в рамках выданной задачи. По умолчанию активен один исполнитель, у каждого изменяемого файла — один владелец. Родитель не редактирует принадлежащие исполнителю файлы до его остановки или явной передачи владения.

Исполнитель не запускает других агентов, не расширяет объём работы, не меняет зависимости и согласованные контракты без решения родителя. Создание зависимых миграций идёт последовательно после проверки текущих миграций; конкурирующие ветки миграций запрещены. До независимого `accepted` исполнитель не выполняет commit/push; после приёмки действует по отдельному ограниченному поручению родителя на версионирование. Нельзя самовольно публиковать приложение, подключать реальные системы вуза или менять секреты и разрешения окружения.

## Как включаются модели

Для новой CLI-сессии модель и усилие задаёт локальный launcher. Для исполнителя в текущей сессии их указывают при запуске.

В текущей сессии родитель явно вызывает инструмент `collaboration.spawn_agent`, например:

```json
{
  "task_name": "task_implementation",
  "fork_turns": "none",
  "model": "gpt-6.1-sol",
  "reasoning_effort": "low",
  "message": "Полная ограниченная постановка по TASK_TEMPLATE.md"
}
```

`fork_turns=none` даёт исполнителю отдельный контекст: родитель передаёт необходимые требования, решения, пути и критерии в `message`, а не рассчитывает на наследование всей беседы. Доступ к общей рабочей директории сохраняется. Исправления передаются тому же исполнителю через `collaboration.followup_task`; уточнения во время работы — через `collaboration.send_message`. Новый исполнитель нужен лишь при завершении или недоступности прежнего и после явной передачи контекста и файлов.

Для будущей сессии из терминала запускают:

```bash
./scripts/codex-project.sh
./scripts/codex-project.sh 'Прочитай README.md и подготовь следующую ограниченную задачу исполнителю'
```

Из другой директории используют абсолютный путь к скрипту. Launcher вычисляет корень относительно своего расположения и передаёт его через `-C`. Он задаёт только для этого запуска:

| Параметр | Значение |
| --- | --- |
| `model` | `gpt-6.1-sol` |
| `model_reasoning_effort` | `high` |
| `agents.enabled` | `true` |
| `agents.default_subagent_model` | `gpt-6.1-sol` |
| `agents.default_subagent_reasoning_effort` | `low` |
| `agents.max_concurrent_threads_per_session` | `1` |

Пользовательские аргументы передаются отдельными аргументами без `eval`; указанные позже явные CLI-переопределения могут изменить эти defaults. Скрипт не изменяет глобальный конфиг, `.codex`, `.agents`, sandbox или политику подтверждений. Он требует установленный и настроенный Codex CLI и доступ к указанным моделям. Настройки будущего запуска не заменяют явные параметры вызова агента в текущей сессии.

Синтаксис `-c key=value` и `-C` проверяется через `codex --help`. Названия настроек основаны на официальной документации [субагентов](https://learn.chatgpt.com/docs/agent-configuration/subagents) и [конфигурации Codex](https://learn.chatgpt.com/docs/config-file/config-reference). Помощь CLI подтверждает синтаксис переопределений, но сама по себе не доказывает запуск моделей или поддержку всех ключей конкретным сервером. При ошибке доступности модели или конфигурации родитель фиксирует блокировку; молча подменять модель нельзя.

## Цикл задачи

По команде пользователя «выполняй далее» родитель сверяет [статус](../../README.md#статус-и-приёмка) и последние ревью с кодом, затем выбирает ближайшую незавершённую задачу с готовыми зависимостями и доводит её до проверяемого результата.

Контрольные точки V1 и V2 описаны в [правилах команды](../../README.md#работа-над-проектом). До обращения к пользователю подготовить адрес и шаги просмотра. В ожидании ответа продолжать независимые задачи. Существенное изменение задачи, расходы без согласованного бюджета и отсутствующие доступы обсуждаются отдельно. Обычные исправления и версионирование принятых этапов разрешены.

1. Родитель читает актуальные требования и архитектуру, проверяет рабочее дерево, определяет один проверяемый результат и владельца файлов. Заполняет [TASK_TEMPLATE.md](TASK_TEMPLATE.md), включая зависимости, контракты, запреты и проверки по риску. В контекст включаются только необходимые разделы и файлы.
2. Исполнитель читает постановку и проектные правила, реализует разрешённый объём, выполняет необходимые проверки и возвращает короткий отчёт: изменённые файлы, команды и результаты, ограничения. Если нужен выход за границы, сообщает родителю конкретное препятствие и ожидает решения по зависимой части; независимую разрешённую работу продолжает.
3. Родитель самостоятельно читает фактический diff и релевантный окружающий код, сверяет контракт и критерии, выполняет достаточные независимые проверки. Самоотчёт исполнителя не заменяет ревью. Проверки межаккаунтного доступа выполняются серверными запросами; мобильность проверяется в браузере от 360 px; сохранение — повторным открытием данных. Применимость определяется задачей.
4. Родитель сохраняет ревью по [REVIEW_TEMPLATE.md](REVIEW_TEMPLATE.md) со статусом `accepted`, `changes requested` или `blocked`. Для замечаний нужны конкретное место, последствие и проверяемое ожидаемое исправление. Тот же исполнитель исправляет их; родитель повторно проверяет изменённые части и риски регрессии.
5. После `accepted` родитель обновляет статус этапа и доказательства. Каждый завершённый этап проходит commit и push по правилам ниже. Принятие кода, локальный commit и подтверждённый push фиксируются отдельно. Принятие отдельной задачи не означает готовность или публикацию прототипа. Для `blocked` указываются недостающий контракт, доступ или внешнее условие и следующий шаг; блокировку нельзя выдавать за выполненное требование.

6. Родитель обновляет раздел «Статус и приёмка» в README, если этап меняет ближайшие шаги или готовность. При внешней блокировке фиксирует условие продолжения. Документацию родитель может подготовить, проверить и закоммитить сам. Прикладной код остаётся ответственностью исполнителя.

## Версионирование завершённых этапов

Пользователь заранее разрешил коммитить и пушить завершённые этапы для поддержания версионирования. После независимого `accepted` родитель поручает исполнителю отдельный ограниченный шаг: ID этапа, ссылку на ревью, точный список файлов для staging, сообщение коммита и согласованную текущую ветку `origin`. Повторное пользовательское разрешение на каждый такой commit/push не нужно. Это разрешение не распространяется на публикацию приложения.

1. Перед записью исполнитель проверяет текущую ветку, `origin`, `git status`, незакоммиченные и уже staged изменения. В общей рабочей директории операции с index, commit и push выполняются последовательно одним владельцем. Чужие staged изменения — причина приостановить этот шаг и согласовать состав с родителем; отменять их или включать в свой коммит нельзя.
2. Проверяет актуальность успешных тестов для принимаемого diff, отсутствие секретов и случайных артефактов. Добавляет только явный список согласованных путей через `git add -- <файл1> <файл2>`. Запрещены `git add .`, массовое добавление несогласованных файлов и сброс чужих изменений. До commit просматривает `git diff --cached --name-status`, полный `git diff --cached` и `git diff --cached --check`; staged diff должен точно соответствовать принятому результату и allowlist.
3. Создаёт осмысленный commit с ID этапа, например `docs(P00): define architecture and implementation plan`. Новый commit нужен только при новых изменениях; пустые коммиты не создаются. При повторной попытке push используется уже созданный commit. Не выполнять force push, не менять уже опубликованную историю через amend/rebase и не обходить защиту ветки.
4. Выполняет обычный push в согласованную текущую ветку `origin`. До push подтверждает, что локальная ветка и согласованное имя совпадают. После успешного push сравнивает SHA локальной ветки (`git rev-parse HEAD`) с SHA соответствующей ветки на сервере (`git ls-remote --heads origin refs/heads/<ветка>`). Только совпадение подтверждает состояние `pushed`; локальная remote-tracking ссылка сама по себе не является проверкой сервера.
5. Записывает отдельно статус ревью `accepted` и статус версионирования: `pending`, `committed / push pending` либо `pushed`, с веткой и фактическим SHA. Если push не удался или проверка SHA недоступна, сохраняет локальный commit, фиксирует ошибку и следующий шаг; не сообщает об успешной синхронизации. При расхождении удалённой истории останавливается и передаёт родителю решение по интеграции.

Авторизация пользователя не отменяет sandbox: защищённый `.git`, ограничения записи и сети не обходят. Если инструмент требует escalation, используется штатный запрос инструмента; внешнее ограничение или отказ фиксируются отдельно от результата ревью кода. Не переключать хранилище Git и не копировать его ради обхода защиты.

## Достоверные материалы процесса

Для каждой задачи сохраняются `docs/evidence/<ID>/prompt.md`, `implementation.md`, `review.md`; при исправлениях — `review-02.md` и далее. В постановке исполнитель получает право писать только свой отчёт, а ревью принадлежит родителю. Для шага версионирования отдельно назначается отчёт `versioning.md`: фактические команды, ветка, commit SHA, результат push и сверки SHA либо причина pending. Такой отчёт, созданный после commit, попадёт в следующий согласованный commit при наличии новых изменений; не менять опубликованный commit ради включения его собственного SHA. В материалах фиксируются реально переданная задача, использованные модель и настройки (с указанием источника: явный вызов или defaults launcher), решения, реальные команды и результаты, замечания и исправления. Ключевые диалоги и скриншоты добавляются со ссылками по мере появления; секреты исключаются.

Не придумывать токены, стоимость, метрики, результаты тестов, опросы или ручные действия. Если телеметрия недоступна, это не мешает принятию задачи: обязательной является достоверность истории, а не выдуманная численная отчётность. Для `SUB-04` отдельно собирается полный перечень реально использованных инструментов и сервисов, включая ручные этапы.
